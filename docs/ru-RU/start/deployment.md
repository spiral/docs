# Начало работы — Развертывание

Развертывание приложения Spiral может быть сложной задачей, поскольку требует выполнения различных шагов для того, чтобы убедиться, что приложение правильно настроено и готово к использованию в продакшене. В этом руководстве мы рассмотрим несколько стратегий развертывания приложения, включая простую передачу файлов, использование системы контроля версий, скрипты сборки и создание Docker-образов.

## Подготовка приложения

Развертывание приложения Spiral на продакшн-сервере требует нескольких ключевых конфигураций для обеспечения правильной работы и безопасности.

> **Предупреждение**
> Не храните файл `.env` в вашем репозитории, поскольку он может содержать конфиденциальную информацию, такую как учетные данные базы данных, API-ключи и другие секреты.

Вот пошаговое руководство по настройке приложения Spiral на продакшн-сервере:

### Отключение режима отладки

Убедитесь, что переменная `DEBUG` установлена в `false` в конфигурации окружения вашего приложения. Это предотвратит отображение конфиденциальной информации в случае ошибки.

```dotenv .env
DEBUG=false
```

### Установка окружения в продакшн

Измените переменную `APP_ENV` в конфигурации окружения вашего приложения на `production`. Это предотвратит случайные действия, которые должны выполняться только на сервере разработки.

```dotenv .env
APP_ENV=production
```

### Включение кэша токенизатора

Убедитесь, что переменная `TOKENIZER_CACHE_TARGETS` установлена в `true` в конфигурации окружения вашего приложения. Это отключит сканирование и анализ исходного кода приложения, что может улучшить производительность при загрузке.

```dotenv .env
TOKENIZER_CACHE_TARGETS=true
```

> **Примечание**
> Подробнее о токенизаторе читайте в разделе [Компоненты — Статический анализ](../advanced/tokenizer.md).

### Установка уровня детализации

Установите переменную `VERBOSITY_LEVEL` на уровень `basic`, чтобы скрыть серверные ошибки от публичного отображения.

```dotenv .env
VERBOSITY_LEVEL=basic
```

### Настройка логгера

Установите желаемый `MONOLOG_DEFAULT_CHANNEL` в конфигурации окружения приложения. Это определит, где будут храниться логи приложения. Также установите переменную `MONOLOG_DEFAULT_LEVEL` в `error` в конфигурации окружения вашего приложения. Это предотвратит логирование ошибок отладки и информационных сообщений, помогая поддерживать логи чистыми и легкими для чтения.

```dotenv .env
MONOLOG_DEFAULT_CHANNEL=roadrunner
MONOLOG_DEFAULT_LEVEL=error
```

### Cycle ORM

Если вы используете Cycle ORM, убедитесь, что переменные `CYCLE_SCHEMA_CACHE` и `CYCLE_SCHEMA_WARMUP` установлены в `true` в окружении вашего приложения.

Переменная `CYCLE_SCHEMA_CACHE` контролирует, должна ли ORM кэшировать схему таблиц базы данных. При установке в `true` ORM будет кэшировать схему, что может улучшить производительность приложения за счет уменьшения количества запросов к базе данных, необходимых для получения информации о схеме.

Переменная `CYCLE_SCHEMA_WARMUP` контролирует, должна ли ORM прогревать кэш схемы при запуске приложения. При установке в `true` ORM будет предварительно заполнять кэш схемы информацией о схеме, что может дополнительно улучшить производительность приложения за счет сокращения времени получения информации о схеме.

```dotenv .env
CYCLE_SCHEMA_CACHE=true
CYCLE_SCHEMA_WARMUP=true
```

### Composer

Следующие команды composer могут использоваться для установки пакетов поставщиков для приложения Spiral:

```terminal
composer install --optimize-autoloader --no-dev --no-scripts
```

Эта команда устанавливает зависимости приложения, генерирует файлы автозагрузчика для приложения и оптимизирует их для производительности.

- Опция `--no-dev` используется для предотвращения установки любых зависимостей разработки
- Опция `--no-scripts` используется для предотвращения выполнения любых скриптов `post-install`.

## Nginx

### Прокси к RoadRunner

Если вы хотите использовать Spiral с RoadRunner и иметь сервер Nginx перед ним, вам нужно настроить Nginx как обратный прокси.

Вот пример настройки Nginx в качестве обратного прокси.

```nginx /etc/nginx/sites-enabled/roadrunner.conf
server {
    listen 80;

    server_name _;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

Эта конфигурация указывает Nginx слушать порт `80` и перенаправлять все входящие запросы на `127.0.0.1:8080`, где работает RoadRunner.

Вы можете поместить этот конфигурационный файл в каталог `/etc/nginx/sites-available/`, а затем создать символическую ссылку на него в каталоге `/etc/nginx/sites-enabled/`.

Вот пример конфигурации, которая использует HTTP-сервер RoadRunner:

```yaml .rr.yaml
http:
  address: 127.0.0.1:8080
```

> **Предупреждение:**
> Избегайте использования адреса: `0.0.0.0:8080` в конфигурации RoadRunner, поскольку это заблокирует прямой доступ к HTTP-серверу RoadRunner, разрешая доступ только через обратный прокси Nginx.

### PHP-FPM

Для использования Spiral с PHP-FPM вам нужно выполнить следующие шаги:

1. Установите пакет `spiral/sapi-bridge`, который предоставляет диспетчер, который PHP-FPM будет использовать для обработки запросов.

Используйте следующую команду для установки пакета:

```terminal
composer require spiral/sapi-bridge
```

После установки пакета вам нужно зарегистрировать загрузчик (Bootloader) `Spiral\Sapi\Bootloader\SapiBootloader` в списке загрузчиков вашего приложения.

:::: tabs

::: tab Используя метод

```php app/src/Application/Kernel.php
public function defineBootloaders(): array
{
    return [
        // ...
        \Spiral\Sapi\Bootloader\SapiBootloader::class,
        // ...
    ];
}
```

Подробнее о загрузчиках (Bootloader) читайте в разделе [Фреймворк — Загрузчики (Bootloader)](../framework/bootloaders.md).
:::

::: tab Используя константу

```php app/src/Application/Kernel.php
protected const LOAD = [
    // ...
    \Spiral\Sapi\Bootloader\SapiBootloader::class,
    // ...
];
```

Подробнее о загрузчиках (Bootloader) читайте в разделе [Фреймворк — Загрузчики (Bootloader)](../framework/bootloaders.md).
:::

::::

2. Настройте Nginx для использования PHP-FPM.

Вот пример того, как вы можете настроить Nginx для работы с PHP-FPM:

```nginx /etc/nginx/sites-enabled/spiral.conf
server {
    listen 80;
    listen [::]:80;
    server_name example.com;
    root /srv/example.com/public;
 
    add_header X-Frame-Options "SAMEORIGIN";
    add_header X-Content-Type-Options "nosniff";
 
    index app.php;
 
    charset utf-8;
 
    location / {
        try_files $uri $uri/ /app.php?$query_string;
    }
 
    location = /favicon.ico { access_log off; log_not_found off; }
    location = /robots.txt  { access_log off; log_not_found off; }
 
    error_page 404 /app.php;
 
    location ~ \.php$ {
        fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }
 
    location ~ /\.(?!well-known).* {
        deny all;
    }
}
```

## Deployer

Использование инструментов автоматизации, таких как [Deployer](https://deployer.org/), может автоматизировать процесс развертывания и обрабатывать такие задачи, как миграции базы данных, очистка кэша и многое другое. Они также позволяют ускорить процессы развертывания и отката, и могут быть интегрированы с другими инструментами, такими как балансировщики нагрузки и системы мониторинга. Это может сделать процесс развертывания более эффективным и менее подверженным ошибкам, и облегчает отслеживание того, какая версия кода в данный момент находится на продакшн-сервере, что упрощает откат в случае ошибок.

Deployer — это популярный инструмент развертывания, который может использоваться для автоматизации процесса развертывания для приложения Spiral. Одним из преимуществ использования Deployer является то, что он может обеспечить развертывание с "нулевым временем простоя".

Развертывание с нулевым временем простоя — это техника, которая позволяет обновлять ваше приложение без прерывания сервиса для ваших пользователей. Это достигается за счет развертывания новой версии приложения рядом со старой версией, а затем их замены, как только новая версия готова. Это обеспечивает плавный переход, поскольку пользователи не затрагиваются никаким временем простоя во время процесса развертывания.

Deployer обеспечивает возможность развертывания с нулевым временем простоя, создавая новый релиз приложения в другом каталоге и переключая символическую ссылку на новый релиз.

### Установка

Для установки Deployer выполните следующую команду в каталоге вашего проекта:

```terminal
composer require --dev deployer/deployer
```

### Конфигурация

Для инициализации deployer в вашем проекте выполните:

```terminal
./vendor/bin/dep init
```

Deployer задаст вам несколько вопросов, и после завершения у вас будет файл `deploy.php` или `deploy.yaml`. Это ваш рецепт развертывания. Он содержит хосты, задачи и требует других рецептов.

Вот пример файла `deploy.php`:

```php deploy.php
namespace Deployer;

require 'recipe/spiral.php';

set('repository', 'https://github.com/xxx/my-app');

add('shared_files', []);
add('shared_dirs', []);
add('writable_dirs', []);

host('example.org')
    ->set('remote_user', 'deployer')
    ->set('deploy_path', '/var/www/my-app');

after('deploy:failed', 'deploy:unlock');

desc('Deploys your project');
task('deploy', [
    'deploy:prepare',
    'deploy:environment',
    'deploy:vendors',
    'spiral:encrypt-key',
    'spiral:configure',
    'deploy:download-rr',
    'deploy:publish',
    'deploy:restart-rr'
]);
```

Для подключения к удаленному хосту нам нужно указать ключ идентификации или приватный ключ. Мы можем добавить наш ключ идентификации прямо в определение хоста, но лучше поместить его в файл `~/.ssh/config`:

```bash ~/.ssh/config
Host example.org
  IdentityFile ~/.ssh/id_rsa
```

Теперь давайте настроим наш сервер. Поскольку на нашем хосте нет пользователя deployer, мы переопределим `remote_user` для провизионирования через `-o remote_user=root`.

```terminal
dep provision -o remote_user=root
```

Deployer задаст вам несколько вопросов во время провизионирования: версия php, тип базы данных и т.д. Затем Deployer настроит наш сервер и создаст пользователя deployer. Провизионирование занимает около 5 минут и установит все необходимое для запуска веб-сайта. Новый веб-сайт будет настроен по пути `deploy_path`.

### Развертывание

Для развертывания вашего приложения выполните следующую команду:

```terminal
./vendor/bin/dep deploy
```

> **Примечание**
> Если развертывание не удалось, Deployer выведет сообщение об ошибке и какая команда была неуспешной. Скорее всего, нам нужно настроить правильные учетные данные базы данных в файле `.env` или подобном.

#### CI/CD

Deployer может использоваться в пайплайнах CI/CD.

> **Узнать больше**
> Подробнее об этом читайте в разделе [Deployer CI/CD](https://deployer.org/docs/7.x/ci-cd).

## Docker

Docker позволяет легко развертывать, масштабировать и управлять контейнерами приложений. Это также упрощает воспроизведение продакшн-окружения и тестирование приложений локально, что облегчает поиск и исправление проблем.

Этот метод включает в себя создание Docker-образа приложения, а затем запуск образа на продакшн-сервере.

### Dockerfile

Вот пример `Dockerfile`, который может использоваться для создания Docker-образа для приложения Spiral:

```dockerfile 
# Этот пример будет работать с корневым каталогом приложения как контекстом docker
FROM php:8.2-cli-alpine3.17 as backend

RUN  --mount=type=bind,from=mlocati/php-extension-installer:1.5,source=/usr/bin/install-php-extensions,target=/usr/local/bin/install-php-extensions \
      install-php-extensions opcache zip xsl dom exif intl pcntl bcmath sockets && \
     apk del --no-cache  ${PHPIZE_DEPS} ${BUILD_DEPENDS}

WORKDIR /app

ENV COMPOSER_ALLOW_SUPERUSER=1
COPY --from=composer:2.3 /usr/bin/composer /usr/bin/composer
COPY ./composer.* .
RUN composer config --no-plugins allow-plugins.spiral/composer-publish-plugin false && \
    composer install --optimize-autoloader --no-dev

COPY --from=spiralscout/roadrunner:latest /usr/bin/rr /app

EXPOSE 8080/tcp

COPY ./ .

CMD ./rr serve -c .rr.yaml
```

Вы можете собрать образ, выполнив следующую команду:

```terminal
docker build . -t my-application:latest
```

После сборки образа вам нужно отправить его в реестр Docker или хаб.

```terminal
docker push my-application:latest
```

Вы также можете пометить образ номером версии, например `my-application:1.0`.

```terminal
docker build . -t my-application:latest -t my-application:1.0
docker push my-application:latest
docker push my-application:1.0
```

### Docker Compose

Одним из преимуществ использования Docker является то, что вы можете управлять переменными окружения для вашего приложения через файл `docker-compose` и внешние файлы `.env`, а не создавать файлы `.env` внутри контейнера.

Вот пример файла `docker-compose.yml`, который может использоваться для запуска приложения:

```yaml docker-compose.yaml
version: '3'
services:
  app:
    image: my-application:1.0
    ports:
      - "8080:8080"
    environment:
      - DEBUG=false
      - APP_ENV=production
      - ...
...
```

### Запуск и остановка приложения

Вы можете запустить приложение, выполнив следующую команду:

```terminal
docker-compose up -d
```

и остановить его, выполнив

```terminal
docker-compose down
```

## Система контроля версий

Популярный способ развертывания приложения — использование системы контроля версий. Это включает подключение вашего продакшн-сервера к удаленному репозиторию, такому как Git или SVN, а затем развертывание приложения путем получения последних изменений из репозитория.

### Пример

1. Подключитесь к продакшн-серверу через SSH
2. Перейдите в корневой каталог вашего приложения на сервере
3. Выполните команду `git pull origin master`, чтобы получить последние изменения из удаленного репозитория
4. После получения изменений выполните `composer install --optimize-autoloader --no-dev` для установки зависимостей
5. Выполните миграции базы данных и другие необходимые консольные команды
6. Перезапустите воркеры сервера RoadRunner `./rr reset`

> **Предупреждение:**
> Использование этой стратегии без автоматизации может сделать процесс развертывания более трудоемким и подверженным ошибкам. Каждый раз, когда требуется развертывание, разработчикам нужно будет вручную получать код из репозитория и выполнять любые необходимые консольные команды в определенном порядке. Это увеличивает риск человеческой ошибки, такой как выполнение команд в неправильном порядке или забывание выполнить команду, что может привести к проблемам с приложением.

## Передача файлов

Один из самых простых способов развертывания приложения Spiral — это простая передача файлов. Это можно сделать с помощью FTP или SCP. Процесс включает загрузку файлов приложения с вашей локальной машины на продакшн-сервер.

### Пример

1. Подключитесь к продакшн-серверу с помощью FTP-клиента (FileZilla, WinSCP)
2. Перейдите в корневой каталог вашего приложения на сервере
3. Выберите все файлы приложения на вашей локальной машине и загрузите их на сервер
4. После завершения загрузки выполните `composer install --optimize-autoloader --no-dev` для установки зависимостей
5. Выполните миграции базы данных и другие необходимые консольные команды
6. Перезапустите воркеры сервера RoadRunner `./rr reset`

> **Предупреждение:**
> Эта стратегия считается менее эффективной и менее безопасной, чем другие методы. Загрузка всех файлов вручную может занять много времени, и существует риск потери или повреждения данных, если передача прерывается. Кроме того, может быть сложно отслеживать, какая версия кода в данный момент находится на продакшн-сервере, что затрудняет откат в случае ошибок.
