# Контейнер — Области видимости IoC

Создание долгоживущих приложений требует правильного управления контекстом. В демонизированных приложениях вы больше не можете рассматривать пользовательские запросы как глобальные синглтоны, хранящиеся в сервисах.

Это означает, что вам нужно явно запрашивать контекст при обработке пользовательского ввода. Spiral предоставляет элегантный способ управления этим с помощью областей видимости контейнера IoC (Инверсия управления).

Области видимости позволяют создавать изолированные контексты, где вы можете переопределять сервисы и управлять их жизненным циклом.

## Создание изолированных областей видимости

Чтобы создать изолированный контекст, используйте метод `$container->runScope()`. Первый аргумент — это объект `Scope`, который содержит опции области видимости, а второй — функция, которая будет выполняться внутри этой области видимости. Результат этой функции возвращается `runScope()`.

```php
$result = $container->runScope(
    new Scope(bindings: [
        LoggerInterface::class => FileLogger::class,
    ]),
    function () {
        // Ваш код здесь
    },
);
```

В этом примере `LoggerInterface` будет разрешен внутри области видимости как `FileLogger`.

## Как это работает

Когда вы вызываете `$container->runScope(new Scope(...), fn() => ...)`, создается новый контейнер со своими собственными привязками. Существующий контейнер становится родителем этого нового контейнера.

Новый контейнер будет использоваться внутри предоставленной функции и будет уничтожен после завершения функции.

Важные моменты:
- **Видимость**: Родительские контейнеры не знают о своих дочерних контейнерах. Однако сервисы в родительском контейнере доступны внутри дочерних.
- **Именование областей видимости**:
  - Основная глобальная область видимости всегда `root`.
  - Именованные области видимости должны иметь уникальные имена в иерархии, чтобы избежать конфликтов.  
    ![scopes-conflict](https://gist.github.com/user-attachments/assets/32f1ae89-9e35-4e7a-9e53-b3db15fee0ea)
  - Параллельные области видимости с одинаковыми именами (как в корутинах) могут существовать и будут иметь свои собственные иерархии.
- При выходе из области видимости связанный контейнер уничтожается.

### Порядок разрешения зависимостей

При разрешении зависимостей внутри изолированной области видимости:
1. Контейнер сначала пытается найти привязку в текущей области видимости.
2. Если привязка не найдена, контейнер пытается найти её в родительской области видимости, и так далее до корневого контейнера.
3. Экземпляр создается в области видимости, где была найдена привязка. Это означает, что зависимости для этого экземпляра разрешаются в той же области видимости.

## Предопределенные области видимости

Spiral предоставляет несколько предопределенных областей видимости:

![spiral-scopes](https://gist.github.com/user-attachments/assets/aa12be0a-bea1-439c-a676-ef8d6158bda9)

1. `root` — Основная глобальная область видимости. Все остальные области видимости являются её дочерними.
2. **Область видимости диспетчера** — Область видимости, которая открывается при запуске соответствующего [Диспетчера](../framework/dispatcher.md): `http`, `console`, `grpc`, `centrifugo`, `tcp`, `queue` или `temporal`.
3. **Область видимости запроса** — Область видимости, которая открывается перед выполнением контроллера, когда объект запроса полностью сформирован и готов к обработке. В случае HTTP-диспетчера посредники (middleware) будут выполняться в области видимости `http`, а перехватчики (interceptors) в `http-request`.

Если вы уверены, что сервис будет работать только в определенном диспетчере, имеет смысл использовать соответствующую область видимости. Например, HTTP-посредники должны быть привязаны на уровне области видимости `http`.

Вы можете создавать свои собственные области видимости для изоляции контекста и обеспечения доступности только определенных сервисов.

## Настройка привязок для именованных областей видимости

Вы можете предварительно настроить привязки, специфичные для именованных областей видимости, используя метод `BinderInterface::getBinder()`. Это позволяет установить привязки по умолчанию для области видимости.

```php
$container->bindSingleton(Interface::class, Implementation::class);

// Настроить привязки по умолчанию для области видимости 'request'
$binder = $container->getBinder('request');
$binder->bindSingleton(Interface::class, Implementation::class);
$binder->bind(Interface::class, factory(...));
```

> **Примечание**
> Привязки в области видимости не влияют на существующие контейнеры этой области видимости (кроме `root`).

## Переопределение привязок по умолчанию

При использовании `Container::runScope()` вы можете передать привязки для переопределения значений по умолчанию для определенной области видимости.

```php
$container->bindSingleton(SomeInterface::class, SomeImplementation::class);

$container->runScope(
    new Scope(
        name: 'request',
        bindings: [SomeInterface::class => AnotherImplementation::class],
    ),
    function () {
        // Ваш код здесь
    }
);
```

Здесь, даже если область видимости `request` имеет привязку по умолчанию для `SomeInterface`, этот конкретный запуск использует `AnotherImplementation`.

## Ограничения области видимости

Вы можете ограничить место разрешения зависимости, используя атрибут `#[Scope('name')]`.

```php
use Spiral\Boot\Environment\DebugMode;
use Spiral\Core\Attribute\Scope;
use Spiral\Core\Attribute\Singleton;

#[Singleton]
#[Scope('http')]
final readonly class DebugMiddleware implements \Psr\Http\Server\MiddlewareInterface
{
    public function process(ServerRequestInterface $request, RequestHandlerInterface $handler): ResponseInterface
    {
        // ...
    }
}
```

В этом примере `DebugMiddleware` может быть создан только если область видимости `http` существует в иерархии областей видимости. В противном случае выбрасывается исключение.

## Уничтожение областей видимости и финализация

При выходе из области видимости связанный контейнер уничтожается. Это означает, что синглтоны, созданные в области видимости, должны быть собраны сборщиком мусора, поэтому избегайте циклических ссылок.

Если вам нужно выполнить действия по очистке при разрешении зависимостей в области видимости, используйте атрибут `#[Finalize('methodName')]` для указания метода, который будет вызван при уничтожении области видимости.

```php
#[Finalize('destroy')]
class MyService
{
    /**
     * Этот метод будет вызван перед уничтожением области видимости в случае, если сервис был разрешен в этой области видимости.
     * Аргументы будут разрешены с помощью контейнера.
     */
    public function destroy(LoggerInterface $logger): void
    {
        // Очистка...
    }
}
```

## Прокси-объекты

Области видимости подобны вложенным контейнерам, но в них есть больше, чем простое делегирование.

Что если вы хотите создать stateless-сервис в родительской области видимости (`root` или `http`), который будет обрабатывать объекты `ServerRequestInterface` в области видимости `http-request`? С вложенными контейнерами это невозможно, поскольку `ServerRequestInterface` доступен только внутри области видимости `http-request`. Более того, `ServerRequestInterface` будет разным для каждого запроса.

Spiral предоставляет прокси-объекты, которые откладывают разрешение зависимостей до тех пор, пока они действительно не понадобятся.

Используйте атрибут `#[Proxy]` для создания прокси для интерфейсов:

```php
use Psr\Http\Message\ServerRequestInterface;
use Spiral\Core\Attribute\Proxy;
use Spiral\Core\Attribute\Singleton;

#[Singleton]
final readonly class DebugService
{
    public function __construct(
        #[Proxy] private ServerRequestInterface $request,
    ) {}

    public function hasDebugInfo(): bool
    {
        return $this->request->hasHeader('X-Debug');
    }
}
```

Важные моменты:
- Прокси настраиваются только для интерфейсов.
- Каждый вызов метода на прокси будет разрешать реальный объект из контейнера.
- Вызов методов, не определенных в интерфейсе, запрещен.

Вы можете настроить прокси для сервисов, которые должны быть доступны только в определенных областях видимости, используя класс `Binder`. Например, если сервис `AuthInterface` должен быть доступен только в области видимости `http`, вы можете использовать прокси-объект для области видимости `root`:

```php
// Настроить прокси для `AuthInterface` в области видимости `root`
$rootBinder = $container->getBinder('root');
$rootBinder->bindSingleton(new \Spiral\Core\Config\Proxy(
    AuthInterface::class,
    singleton: true,
    fallbackFactory: static fn() => throw new \LogicException(
        'Невозможно получить экземпляр AuthInterface вне области видимости `http`.'
    ),
));

// Привязать `AuthInterface` в области видимости `http`
$container->getBinder('http')
    ->bindSingleton(AuthInterface::class, Auth::class);
```

Если прокси используется вне области видимости `http`, будет вызвана `fallbackFactory` для разрешения зависимости. Если `fallbackFactory` не предоставлена, будет выброшено исключение `RecursiveProxyException`.
